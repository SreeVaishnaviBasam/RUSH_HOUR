Requirement 01
Never sell the
501st unit
The Problem

5,000 requests arrive simultaneously. All read "1 unit left". All try to buy. Without protection: -4,999 stock.

The Solution

An async Mutex forces all checkouts through a single lane. Inside the lock, a single SQLite transaction checks AND decrements stock atomically. By the time request #101 enters, stock is 0.

📁 src/lib/mutex.ts 📁 src/app/api/checkout/route.ts
checkout/route.ts 
// Mutex: only 1 checkout at a time
const result = await checkoutMutex
  .runExclusive(async () => {
    return await prisma.$transaction(async (tx) => {

      // ① Check available stock
      const product = await tx.product
        .findUnique({ where: { id: productId } });

      if (product.available < quantity) {
        return { error: 'Sold out', status: 409 };
      }

      // ② Atomically decrement
      await tx.product.update({
        where: { id: product.id },
        data: { available: { decrement: quantity } },
      });

      // ③ Create reserved order
      const order = await tx.order.create({
        data: { productId, buyerId, status: 'reserved' }
      });
    });
  });
Requirement 02
Same request twice
= one order
The Problem

Double-click, network retry, browser re-submit. Without protection: same buyer gets charged multiple times and stock drops twice.

The Solution

Every Buy click generates a UUID idempotency key. The database has a @unique constraint on it. If the same key arrives again, we return the existing order — no new charge, no stock decrement.

📁 prisma/schema.prisma 📁 src/app/api/checkout/route.ts
schema.prisma + checkout/route.ts

}

    orderId: existing.id,

    statusCode: 200,

}

Requirement 03
Hold stock,
release if stall
The Problem

A buyer starts checkout, payment hangs, browser closes. Without recovery, that stock is permanently locked — unsellable to anyone.

The Solution

On checkout, we set expiresAt = now + 90 seconds. A background Expiry Sweeper runs every 500ms, finds expired orders, marks them expired/failed, and returns stock to the pool — all in one atomic transaction.

📁 src/lib/worker.ts → runExpirySweeper()
src/lib/worker.ts 
async function runExpirySweeper() {
  try {
    const expired = await prisma.order.findMany({
      where: {
        status: { in: ['reserved', 'payment_pending'] },
        expiresAt: { lte: new Date() }, // past deadline
      },
    });

    await prisma.$transaction(async (tx) => {
      // Mark orders expired
      await tx.order.updateMany({
        where: { id: { in: ids } },
        data: { status: 'expired' },
      });

      // Return stock per product
      for (const [productId, qty] of byProduct) {
        await tx.product.update({
          where: { id: productId },
          data: { available: { increment: qty } },
        });
      }
    });
  } finally {
    // Recursive — waits for DB before next run
    setTimeout(runExpirySweeper, 500);
  }
}
Requirement 04 + 05
Payments fail & hang.
State recovers cleanly.
The Problem

Real payment gateways fail 20% of the time and hang indefinitely another 20%. Both must result in clean stock recovery — never corrupted state.

The Solution

Mock chargePayment() returns success 60%, failure 20%, hangs 10s (20%). The Batch Writer refunds stock AND marks order failed in the same transaction. Hangs are caught by the Expiry Sweeper after 90s.

// Mock payment gateway
async function chargePayment() {
  const rand = Math.random();
  if (rand < 0.6) return 'success'; // 60%
  if (rand < 0.8) return 'failure'; // 20%
  await sleep(10000); // 20% hang — sweeper resolves
}

// Batch Writer — failure path
if (failedItems.length > 0) {
  await tx.order.updateMany({
    where: { id: { in: failedIds } },
    data: { status: 'failed' },  // ① mark failed
  });

  // ② refund stock per product
  for (const [productId, qty] of byProduct) {
    await tx.product.update({
      where: { id: productId },
      data: { available: { increment: qty } },
    });
  }
  // Both in same transaction → atomic
  // Can never fail halfway
}
Requirement 06
Slow work off
the request path
The Problem

Payment takes 200–700ms (or 10 seconds if it hangs). Making the buyer wait for that blocks the server and kills UX.

The Solution

Checkout returns in <100ms with a reserved order ID. Three recursive background loops handle everything else — expiry, payment, and batch writes. All use setTimeout (not setInterval) so slow DB writes never stack up.

Requirement 07
Live buyer screen
with honest status
The Problem

The buyer needs real-time feedback. But status changes happen in the background. How does the UI stay honest without lying or going stale?

The Solution

Stock bars poll /api/stock every 2 seconds. After checkout, an order status card polls /api/orders/[id] every 1 second until a terminal state. All reads are direct DB queries — no cache, never stale. Hold countdown timer shows seconds until expiry.

Requirement 08
Rate limit
per user
The Problem

A bot or angry buyer spams Buy 1,000 times a second, clogging the mutex queue and potentially gaming the system.

The Solution

Token Bucket per buyerId. Each user gets 5 tokens (burst), refilling at 3/second. Each checkout costs 1 token. Empty bucket → HTTP 429 with exact retryAfterMs so the UI shows a countdown. Admin sees who's been blocked most.

📁 src/lib/rateLimiter.ts Capacity: 5 tokens · Refill: 3/sec
src/lib/rateLimiter.ts 
const CAPACITY = 5;
const REFILL_RATE = 3 / 1000; // 3 tokens/sec

export function checkRateLimit(buyerId) {
  const now = Date.now();
  let bucket = rateLimiterMap.get(buyerId);

  if (!bucket) {
    bucket = { tokens: CAPACITY, lastRefill: now };
    rateLimiterMap.set(buyerId, bucket);
  } else {
    // Refill tokens since last request
    const elapsed = now - bucket.lastRefill;
    bucket.tokens = Math.min(
      CAPACITY, bucket.tokens + elapsed * REFILL_RATE
    );
    bucket.lastRefill = now;
  }

  if (bucket.tokens >= 1) {
    bucket.tokens -= 1;
    return true;  // ✅ allowed
  }
  return false;   // 🚫 429
}
